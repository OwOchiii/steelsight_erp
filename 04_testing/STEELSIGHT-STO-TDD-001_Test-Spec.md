**Severity:** `CRITICAL`

**Legal:** `Luật 91/2025/QH15 — sensitive data isolation`

**TDD Phase:** 🟢 GREEN

**Oracle Source:** `BR-STO-002`, `BR-STO-003`

### STO-TC-INT-001 — An old face photo is removed only after its replacement or the deletion commits

**Severity:** `HIGH`
**Feature Under Test:** Full flow: `UserService.changeFacePhoto/softDelete` → `TransactionSynchronization.afterCommit` → `PhotoStorage.delete(FACE, old)`
**Test File:** `FacePhotoCleanupTest.java` — `anOldFacePhotoIsRemovedOnlyAfterItsReplacementOrTheDeletionCommits`
**TDD Phase:** 🟢 GREEN
**Condition Ref:** `TC-COND-008`

**Preconditions:** Testcontainers PostgreSQL; local storage folder; the test commits for real (no class-level rollback), so names are made unique per run

**Test Steps:**
1. Admin creates a worker with a face photo through `POST /team/new` → file 1 exists in `faces/`
2. Admin uploads a new face photo through `POST /team/{id}/face` → path changes; file 1 is gone, file 2 exists
3. Admin deletes the worker (`confirm=true`) → file 2 is gone; no `face_embedding` row

**Expected Result (PASS):** each old file disappears once the change that replaced or removed it has committed
**Expected Result (FAIL):** old photos pile up (biometric data kept), or the current photo is deleted

**DB Assertion:**
```java
assertThat(FACES.resolve(first)).doesNotExist();
assertThat(jdbc.queryForObject("SELECT count(*) FROM face_embedding WHERE user_id = ?", Integer.class, worker)).isZero();
```

> Not covered: that a **rolled-back** change keeps the old file. That path is in `UserService.removeFacePhotoAfterCommit` but untested — see STO-TC-033.

**Current Status:** 🟢L
