## Where it can still be abused
All of these need a leaked key, except the first, which needs no key:

1. **No rate limit:** anyone can send unlimited guesses at the key. The guessing itself is harmless with a strong key, but it still creates load and fills the logs with warnings.
2. **Real alerts can be silenced:** any new alert starts the 15-minute quiet period (`SafetyAlertService.java:49`). With a stolen key, one fake alert every 15 minutes means HSE is never notified of real ones, which is the worst case here.
3. **Unlimited database rows:** each new `eventId` adds a row, and valid calls have no rate limit either.
4. **Replayed or faked data:** a captured request can be modified and sent again with a new `eventId`, and `detectedAt` and `violationCount` have no upper bounds.

## What I recommend, in order
1. **Check the key today:** generate it with `openssl rand -base64 32`, and make sure `DETECTION_ERP_URL` uses `https://`. Keep it only in Render's environment settings and the detection machine's `.env`. I can't see either of those values from here.
2. **Add rate limiting to `/api/**`:** put it before the key check, per client IP, at around 30 requests a minute. `SignInLimiter` may be reusable for this.
3. **Stop unverified alerts from silencing real ones:** start the quiet period only when an alert is plausible, and track it per camera. One bad source then can't mute the whole site, and `detectedAt` must be within a few minutes of the current time.
4. **Sign requests with HMAC:** the detection server sends `X-Timestamp` and `X-Signature: HMAC-SHA256(secret, timestamp + "." + rawBody)`, and `ApiKeyFilter` rejects anything older than 5 minutes. The secret never travels with the request, and captured requests can't be altered or replayed later. It doesn't help if the detection machine itself is compromised, and it needs a matching change in the detection codebase.

If the site has a static IP, also allowlist it in front of Render, since that blocks nearly everything else. If you ever run the ERP on the same machine as detection, set `server.address: 127.0.0.1`, because no address is set now and it listens on all interfaces.

## What changed
**Rate limiting** (`security/ApiLimiter.java`, used by `ApiKeyFilter`)
- A caller with the right key gets 60 calls a minute, and each address gets 10 wrong-key attempts a minute. Over either limit, the API returns 429 with `Retry-After`.
- Wrong-key attempts are counted separately and can't block your detection server, even if an attacker fakes its IP.

**Alert silencing** (`SafetyAlertService`)
- Each registered camera now has its own 15-minute quiet period, so a fake alert can't mute the whole site.
- Unknown or missing camera codes share one quiet period, so made-up codes can't flood HSE.
- An alert detected more than 1 hour ago or more than 5 minutes in the future is saved, but doesn't notify anyone or start a quiet period.
- `violationCount` above 100,000 or `windowSeconds` above 86,400 now returns 400.

I also updated ADR-019 and the notification design doc, whose "no rate limit" notes were out of date.

## JWT: I wouldn't add it
- **For the detection API:** a JWT still needs a secret to sign it, so you'd have the same leak risk plus more code. It suits many users or services logging in through a central system, and here you have one machine calling one endpoint.
- **For the website:** your login uses server sessions, which fit a server-rendered app better because you can end a session immediately. JWTs are hard to revoke before they expire.

The better next step is HMAC request signing (item 4 from before), because it blocks altered or replayed requests.

> **Correction (added 12 November 2026, after code review):** HMAC signing blocks altered requests, but on its own it doesn't stop replays. Checking the signed timestamp only limits a replay to the acceptance window, 5 minutes in item 4: a captured request can be sent again, unchanged, within that window. Preventing replays also needs the server to remember a unique ID for each request, such as a nonce, and refuse one it has already seen, or an equivalent idempotency mechanism. For the alert API, `eventId` already plays that role: a repeated `eventId` is answered 200 and creates nothing (ADR-005, ADR-019). HMAC signing hasn't been built.
