### Worker timetable grid, safety scores, notifications and detection alert API

#### Context
- The worker timetable is two flat lists, and it should be a grid like the manager's.
- Violations have no consequences yet. Workers need a monthly safety score with warning and danger notifications.
- Managers need to see every worker, but only schedule and resolve tickets for their own team.
- HSE needs all worker scores, a per-shift view of how unsafe each time slot is, and an alert when detection sees too many violations.

Facts from the code that shape the design:
- The Python detection software writes violations **directly to Postgres**, so ERP Java code never sees a new violation.
- The ERP can sleep on Render and has no scheduler.
- No notification system and no REST API exist yet.

Decisions already made with the user:
- The score resets on the 1st of each month.
- Repeat hits lose points at most once per 30 minutes.
- A "shift" for HSE is a site-wide time slot, because one overview camera covers the site.
- Detection counts violations in memory, decides when it's critical, and calls the ERP API.

#### Defaults to confirm (all stored in one table, easy to change)
| Setting | Default | Effect |
|---|---|---|
| Points lost per counted violation | 10 | |
| Warning | score ≤ 70 | 3rd counted violation in a month |
| Danger | score ≤ 40 | 6th counted violation in a month |
| Score floor | 0 | |

- A violation loses points as soon as it's detected, including while disputed. If HSE overturns it, the points come back.
- A violation with no identified worker loses no points until HSE assigns one.
- If HSE assigns a worker to a violation from an earlier month, the current score doesn't change.

#### 1. Worker timetable grid
- `GET /timetable?week=` shows one week as a 7-column table, using the manager grid's `.week-nav`, `.grid-scroll`, `.shift-grid` and chip styles.
- There is one row of days, with no Person column, and total hours in the header. Past shifts are reached with the previous-week link, which replaces the "Upcoming" and "Earlier" lists.
- Chips are plain, not links, because `/shifts/{id}/edit` is manager-only. Cancelled and completed states stay visible.
- On phones the table scrolls sideways, like the manager grid.
- Add `ShiftService.listOwnInRange` (requires `SHIFT_READ_OWN`) and split a `cells(...)` helper out of `web/ShiftGrid.java` so both grids share it.
- Files: `web/TimetableController.java`, `templates/timetable.html`, `timetable.*` messages in both bundles.

#### 2. Safety score: `V8__safety_score_and_notifications.sql`
**No stored score column and no extra per-worker table.** The score is calculated from the violation rows:
- The monthly reset needs no job, so it still happens if the ERP is asleep.
- An overturned violation restores its points automatically.
- The score is `NULL` for anyone whose role isn't `WORKER`, which gives the nullable behaviour without a column.

Schema:
- `safety_policy`: one row holding points, thresholds, the 30-minute limit and the site time zone.
- `safety_score(user_id, at)` and `safety_scores(at)` SQL functions.
  - Score = `100 − points × COUNT(DISTINCT (type, date_bin('30 minutes', detected_at)))`, floored at 0.
  - They count violations from this calendar month in site time, excluding `OVERTURNED`.
  - Thirty-minute blocks are fixed, so two hits either side of a block boundary can both count. That's an accepted trade-off for a much simpler query.
- `notification`: `user_id`, `kind` (`SAFETY_WARNING`, `SAFETY_DANGER`, `HSE_VIOLATION_ALERT`), `score`, `period` (month), `safety_alert_id`, `read_at`, `created_at`. A partial unique index allows one warning and one danger per worker per month.
- `AFTER INSERT OR UPDATE OF user_id, dispute_status` trigger on `violation`.
  - It's `SECURITY DEFINER` with a fixed `search_path`, because the detection role can't write to `notification`.
  - It uses a trigger because detection's direct inserts bypass Java. It also runs when the ERP is asleep and when HSE assigns a worker later.
  - It inserts the most severe level reached, using `ON CONFLICT DO NOTHING`, and skips overturned rows.
- `afterMigrate__enable_rls.sql` already covers the new tables.
- Violations already in the database affect scores right away, but they only trigger a notification on the worker's next violation.

#### 3. Notifications

- Text is **not stored**. It's rendered from `kind` and `score` in the reader's language, so both English and Vietnamese work.

  - **Danger:** the same, plus "your paycheck may be deducted under company policy". It's a heads-up only, with no payroll logic.
- Workers see their own score on the home page and `/violations`.
- In-app only. Email needs an SMTP setup and isn't included.

#### 5. Detection alert API
```
POST /api/v1/detection/alerts
X-Api-Key: <key>
{ "eventId": "uuid", "violationCount": 7, "windowSeconds": 60,
  "detectedAt": "2026-11-05T09:30:00+07:00", "cameraCode": "CAM-B2" }   // cameraCode optional
```
- Responses: `201` created, `200` retry of a known `eventId`, `400` invalid, `401` bad key, all as JSON.
- **Security:** a separate `@Order(1)` filter chain for `/api/**` in `security/SecurityConfig.java`. It's stateless with CSRF off for this chain only, and returns 401 rather than a login redirect. The key comes from env var `STEELSIGHT_DETECTION_API_KEY`, is compared in constant time, and if it's unset every call is refused.
- **Storage:** `safety_alert` table with a unique `event_id`, the same retry-safe pattern detection already uses. `camera_code` is plain text, so a mistyped code can't lose a safety alert.
- **Delivery:** every active HSE officer gets a `HSE_VIOLATION_ALERT` notification. Alerts within 15 minutes of the last one are stored but don't notify again, so a long bad spell doesn't flood the bell.
- **Python side (not in this repo, separate change):** count in memory, call this endpoint when critical, and send it through the existing outbox with a long timeout, because the first call may have to wake the ERP on Render.
